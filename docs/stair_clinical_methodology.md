# STAIR-Clinical — Methodology and Deviations from the Original STAIR

## 1. Original STAIR (reference)
*STAIR (STructure Aware Information Retriever): A novel dataset and LLM based retriever for document structure augmentation*, arXiv:2609.03874v2 (2026). PDF SHA-256 of the copy read for this work: `42dcd80ff2320446da6e55b6660c8655e1b8e33ec44e977ec045d86f398971db`.

What the paper does, as read from the paper:
- **Task:** given a long document D with Table of Contents ToC_D, retrieve the **single leaf node** T_l whose content answers query q.
- **Input / output:** prompt = instruction + `### Book` + full ToC + `### Query` + `### Section: leaf`; completion = the leaf title (paper Table 2).
- **Training:** supervised fine-tuning on synthetic queries mapped to gold leaves (questions generated by Mixtral-8x7B per paragraph). The model learns both the corpus content (DSI-style knowledge ingestion into parameters) and the task of picking a leaf from the ToC.
- **Configuration:** Mistral-7B-Instruct-v0.2, LoRA r=16, α=32, up to 200 epochs, early stopping (patience 20) on dev Recall@1, max input 14k tokens, max output 64 tokens.
- **Inference:** constrained generation restricted to valid ToC leaves. The paper reports hallucination (non-leaf output) below 0.05%.
- **Benchmark:** SearchTome (18 books, 6 domains); STAIR R@1 82.6 vs DSI 76.9, DPR 68.7, BM25 59.5, Mistral out of the box 13.8.

The official code (`github.com/meghanadhpulivarthi/stair-clean`) has **no licence file**, so no code was copied from it. The unofficial reproduction `mithilai/stair-toc-retrieval` (MIT) was not used.

## 2. What STAIR-Clinical keeps
| Element | Original STAIR | STAIR-Clinical |
|---|---|---|
| Retrieval unit | ToC leaf | Hierarchy leaf / concept group of the patient record |
| Input | instruction + ToC + query | instruction + **patient ToC** + query (same template shape, `backend/stair_retriever/prompts.py`) |
| Output | leaf title (`12.9 Step seven…`) | numbered leaf title (`3.1 Current Medications`, `6.1.4 Creatinine…`) |
| Validity | constrained to valid leaves | constrained scoring over **this patient's** valid leaves (`constrained.py`); every path is re-validated against the database before resolution |
| Fine-tuning | LoRA r=16, α=32 | same LoRA hyper-parameters (`train_lora.py`) |
| Metrics | R@1, R@3, nDCG@3, hallucination rate | same + record-level Recall@k, MRR, nDCG@10, invalid path rate, leaf exact match |

## 3. Deliberate modifications (and why)
1. **The ToC is the patient record, not a book.** It is built per patient at query time from the database (`PatientMemory.toc()`). Levels 1–2 form a stable 23-leaf clinical skeleton (`hierarchy.py`). Level 3 holds dynamic concept groups (e.g. one node per lab test or medication ingredient) and is annotated with record counts and date ranges.
2. **No parametric memorization of patient data (DSI component removed).** The original STAIR stores book content in model weights. Patient records change, so STAIR-Clinical learns only the routing skill: mapping a question onto the stable hierarchy. Patient content arrives in-context through the ToC and is resolved from the database. New uploads update the database and ToC immediately with no retraining. *Consequence:* STAIR-Clinical cannot answer from memorized content, and it is not expected to match STAIR's book-level knowledge-ingestion behaviour.
3. **Multi-path, top-k selection.** Clinical questions need several evidence paths (medications *and* the symptom episode). Multi-gold queries are expanded into one SFT example per gold path. At inference all valid targets are scored, normalized with softmax, and kept until cumulative mass ≥ 0.85 (max 3 sections, max 4 groups per section).
4. **Iterative two-stage routing.** Stage 1 routes over sections (levels 1–2). Stage 2 routes over the concept groups of each selected section. This keeps prompts short (mean about 790 tokens in stage 1, measured), which matters on CPU. The paper used a single 14k-token prompt.
5. **Constrained decoding as exhaustive candidate scoring.** Instead of trie-masked beam search, we compute log P(candidate | prompt) for every valid target using a shared prompt KV cache. Ranking by sequence log-probability is equivalent to constrained decoding over the set of valid strings, gives a full ranking for free, and makes invalid outputs impossible by construction. Free (unconstrained) generation is still run on a sample to report the invalid-path rate.
6. **Structured operations stay exact.** STAIR routes; it does not replace database logic. Date ranges, "medications in effect during episode X", and "latest value" are deterministic operations (`patient_retriever.py`).
7. **Hybrid fusion.** STAIR-routed records are fused with BM25+BGE-M3 hybrid results via RRF (weights 1.0 / 0.5) for the app (B4/B5). Pure STAIR is also evaluated on its own.
8. **Selector backends.** `lora` (fine-tuned adapter), `ollama_zero_shot` (free generation, parsed and validated; invalid outputs counted), and `structural` (no LLM: BM25 + BGE-M3 over ToC titles and descriptions plus an intent prior). The structural backend is a non-learned STAIR-style router and is reported as such.

## 4. Training data (Stage 2 of the pipeline)
`backend/stair_retriever/training_data.py` creates questions from real Synthea records in 14 categories (medications during a previous symptom episode, relevant history for a new symptom, organ-system labs, similar previous symptoms, current medications, allergy check, lab trend, latest measurement, medication changes, condition status, last visit, procedure, immunization, diagnoses in a year). Each category has 2–4 paraphrase templates (first person and third person, lay names). **Gold evidence is computed by deterministic database queries, never by an LLM.** Gold = up to 3 most recent records per gold concept group. The split is assigned by `sha256(patient_id)` bucket (70/15/15), so no patient appears in two splits (asserted).

Curated clinical maps used for gold (`query_understanding.py`): `SYMPTOM_RELATED_CONDITIONS` and `SYSTEM_LABS`. The same lexicon also powers query expansion in **every** hybrid and STAIR variant, so it does not favour STAIR. It is a documented confound for absolute numbers, because gold and retrieval share these clinical associations.

## 5. Medical-reference STAIR
The reference corpus keeps Source › Chapter (MedlinePlus topic group) › Section (health topic) › Subsection (`<h3>`) › paragraph. `ReferenceIndex.search(mode="stair")` routes the query to the top-4 sections by fusing BM25 and BGE-M3 over section descriptors (title, meta description, subsection headings). It then retrieves supporting passages only inside those sections. This is non-parametric structure-aware routing; a fine-tuned reference selector was not trained (see training_methodology.md).
